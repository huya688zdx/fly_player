## 2. 总体职责：账号、播放、增强能力分别由谁负责

播放器已有飞牛与 Emby 等媒体后端播放能力。接入飞翔服务后，统一账号负责确认用户能访问哪些绑定、媒体服务器身份以及当前来源，而原媒体后端仍负责原有播放信息、直链或服务端播放会话、音轨字幕和媒体读取。飞翔服务提供的数据增强包括统一目录、统计同步、已确认弹幕、已发布 OPED、BIF 缩略图以及资料助手。增强功能需要依附于精确来源身份，但不应该成为视频解码的前置条件。

关键入口分别是 [FlyAccountController](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_account_controller.dart:18)、[FlyDataService](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_data_service.dart:66)、[MediaPlaybackSourceBridge](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/media_backend/playback/media_playback_source_bridge.dart:20) 与 [MpvMediaSource](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/playback/playback_source.dart:41)。账号控制器管理可见状态、切换和绑定；数据服务持有飞翔会话并包装请求；桥接器将后端中立播放事实装配为播放器源；播放源承载媒体 URL、原媒体 headers、轨道、版本、播放方式及统计范围。

这种分工带来一个重要限制：不能把“飞翔已登录”当成“当前视频已经具有文件级证明”。统一账号验证的是访问关系；FileContext 验证的是某个 binding、remote item、media source 对应的实际文件修订和时间坐标。节目名相同、季集号相同、目录中同属一个标题，都不足以自动复用 OPED 或 BIF。反过来，两个媒体后端若经过完整文件证明确认读取相同字节，可以共享该文件的已生成资源，但来源授权仍须逐个绑定检查。

业务分析应特别关注依赖方向：媒体后端抽象不能反向依赖某个平台播放器实现，平台播放壳不应拿到飞翔 bearer 去自行拼接任意下载地址，模型资料结果也不应直接绕过人工确认改变播放时间线。当前 BIF 采取 Dart 验证下载、平台只接收本地路径，就是在延续这些边界。

## 3. 三组身份与一次播放的范围

代码里至少有三组不能混淆的身份。第一组是飞翔 service instance、用户和本安装设备。第二组是飞翔媒体绑定以及远端媒体服务器的用户和条目。第三组是实际文件修订、媒体时间坐标以及这一轮播放的 generation。把它们压成一个“当前账号”变量，会使异步回调、跨来源缓存和离线上传都难以保证归属。

[FlyDataSession.accountKey](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_data_service.dart:36) 优先由 serviceInstanceId 与 userId 组成；只有旧会话尚没有实例身份时才退回 URL。deviceKey 则由 installationId 与服务器返回的 deviceId 组成。其含义是：同一个服务换局域网、外网或 VPN 地址，逻辑用户不一定变化；复制出来的服务虽然实例身份相同，也不意味着它新建的设备、token、上传流会自动存在于正式数据库。

[PlayStatsService.scopeForBinding](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/play_stats/play_stats_service.dart:76) 再把 accountKey 与 bindingId 一起散列为统计 scope。远端 item ID 只在绑定内有意义，不能把 Emby 的条目编号与飞牛 GUID 放在同一无范围索引里。这个范围也随播放源一起传给 Windows 与 Android，供后续反向调用核对。

| 身份字段 | 管理位置 | 用途 | 不能替代的对象 |
| --- | --- | --- | --- |
| serviceInstanceId、userId | FlyDataSession | 飞翔账号与服务归属 | 不能证明媒体字节相同 |
| installationId、deviceId | 安全凭据与登录响应 | 登录设备、上传流归属 | 不是播放 session_id |
| bindingId、bindingRevision | 账号控制器、媒体连接 | 远端账号授权版本 | 不是 FileContext 修订 |
| remoteItemId、remoteMediaSourceId | FlySourceRef | 精确远端单集与版本 | 不用标题代替 |
| fileRevisionId、mediaCoordinateId | FileContext | 原文件字节和时间坐标 | 不代表当前 UI 仍在该文件 |
| loadNonce、source generation | 播放器上下文 | 防止同 ID 重进及迟到回调 | 不是后台长期任务编号 |

[FlySourceRef](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_oped.dart:12) 输出 binding_id、remote_item_id、remote_media_source_id；最后一个可以为 null。其 matches 方法逐项比较，不使用标题、时长近似或者目录合并结果猜测来源。[FlyPlaybackServiceClient.sourceRef](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_playback_service_client.dart:22) 还检查当前统计数据库的 bindingReference、当前 scope，以及由当前账号加绑定计算的预期 scope。因此，从未关联飞翔的传统媒体连接开始播放时，视频可以继续工作，但不能悄悄借用上一个飞翔账号的增强数据。

## 4. 启动、登录方式与多个入口

[main.dart 的 ProviderGate](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/main.dart:648) 是理解入口行为的起点。FlyAccountController 在应用提供者体系中恢复登录与来源；没有飞翔会话时显示 FlyLoginScreen，存在统一账号但尚未选定有效来源时进入账号来源管理；用户主动选择传统媒体账号模式后，入口按保存的模式恢复。这里的“传统媒体模式”不是退出一切账号，而是明确让原本的媒体连接和统计范围继续由旧提供者管理。

[restore](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_account_controller.dart:83) 先读取登录方式，再恢复安全会话。若保存的是 media 模式，它会先让本地入口可用，并保留飞翔账号和绑定列表用于用户明确返回；不会在延迟恢复完成后自动把用户正在使用的传统连接改成飞翔绑定。若保存的是 fly 模式，恢复的连接必须同时匹配 accountKey、selected binding、已认证状态、binding revision，以及绑定 active/offline 状态，才可能成为当前媒体连接。

[login](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_account_controller.dart:136)、logout、enterLegacyMode、returnToFlyMode 都经过控制器的串行执行尾链，并递增同步 epoch。登录前先排空本地统计写入；登录成功后清理旧活动访问、刷新新账号绑定，再将登录方式保存为 fly。退出即使远端注销请求失败，也要在 finally 中清理本地活动会话和连接，避免界面显示退出而旧凭据仍继续提供增强能力。

传统模式的切换不应该被描述成“迁移历史”。enterLegacyMode 会解绑当前统计作用域并清理飞翔兼容访问副本，但本地历史事实仍然留在各自的数据库里。returnToFlyMode 只是回到统一账号入口，仍需要用户选择正确绑定，不会把原本传统连接里的历史自动认领到统一账号。这一层是后续避免串账号统计的基础，不是可随意删去的 UI 繁琐步骤。

可见入口包括首次登录页、账号与媒体来源页面、桌面来源菜单、设置中的账号管理、统一目录进入原详情，以及传统媒体模式回到飞翔。入口多不意味着状态机多套；应尽量通过同一个控制器执行激活、退出和地址验证。未来若新增电视遥控入口或独立原生窗口，仍应复用这些操作，不另写一份仅修改偏好字段的快捷登录。

## 5. 登录记录、安全存储与服务地址

[FlyLoginScreen](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/screens/fly_account_screen.dart:135) 提供服务根地址、账号、密码、记住密码、登录历史及设备名称。登录历史不是一个无条件回填的全局密码框。修改已保存记录的地址或账号，会使原记录对应的密码失效；旧密码不能随新的地址一起发送。点击历史记录时也需要再次核验服务实例，防止同一个地址后来指向另一台服务。

[FlyDataService.login](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_data_service.dart:106) 的实际顺序是：规范化根地址，读取或创建 installationId，先 GET /system/identity，再 POST /auth/login。若传入 expectedInstanceId 而公开身份不一致，就在发送密码前拒绝；登录响应中的 service_instance_id 也必须与刚验证的实例一致，才能保存会话。保存的登录记录若失败，不推翻已经成功的认证，但向界面保留可见 warning，避免用户误以为密码已经持久化。

[FlyLoginHistoryStore](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_login_history_store.dart:55) 最多保留十条记录，写操作串行。元信息与密码分开处理，密码键绑定记录身份及规范化地址。忘记密码动作删除对应安全存储项；更新地址时清理原地址与新地址关联的密码残留。安全存储暂不可读时，不把它误当成空记录而覆盖原有历史，这是“设备解锁或密钥后端暂时不可用”场景的重要区分。

[SecureCredentialStore 的状态接口](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/secure_credential_store.dart:7) 区分 value、missing、unavailable。Windows 使用 [WindowsSecureCredentialBackend](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/secure_credential_store_windows.dart:19)，通过当前 Windows 用户范围的 DPAPI 加密，把密文放入偏好存储；Android 通过原生安全凭据后端。不能因为磁盘上存在 JSON 就认定其中是明文口令，也不能把 DPAPI 密文文件复制到别的 Windows 用户后假定仍可解密。

## 6. 绑定激活与局域网、外网、VPN 地址选择

绑定激活入口 [FlyAccountController.activate](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_account_controller.dart:308) 首先以 expected_revision 请求 /bindings/{id}/device-access，再核对返回的 binding_id 与 binding_revision。服务器若已重新授权、撤销或更新绑定，旧卡片不能直接继续使用已有媒体访问数据。当前代码允许 active 或 offline 绑定进入激活流程，但最终媒体身份和访问是否可用仍要实际核验。

地址选择不是从偏好缓存中拿一个上次成功 URL 就用。[selectFlyMediaAddress](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_media_address_selector.dart:15) 只接受新授权响应中的 client_lan、client_remote、vpn 地址，按优先级排序、去重，并把仍在授权集合中的首选地址前置。显式手选地址也必须属于本次授权集合。被管理员移除的旧地址不能仅因本地偏好仍保存它而恢复权限。

单次地址探测预算三秒，总预算十二秒，候选数量也有限制。验证器使用独立严格传输，先读媒体服务器公开身份，完全不携带飞翔 bearer、媒体 token、cookie 或登录密码。飞牛探测读取公开 server info 中的 guid；Emby 等读取公开 System/Info/Public 中的 Id。协议所需的公开签名头不等于媒体账号凭据。只有实际身份与绑定中 remote_server_id 相等，才把新下发的远端 access token 应用到连接。

[applyConnection](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_account_controller.dart:361) 先调用 bindMediaBinding 建立统计范围，再保存媒体连接。对于飞牛，它还维护 legacy NasProvider 需要的兼容访问副本，并用 fly.nas_compat_binding 标记归属，以便崩溃恢复、换账号或绑定失效时清理。这里复制的是必要的访问能力，不是让旧提供者重新以媒体用户名认领统计数据库。对其它后端则清除该兼容副本，避免残留飞牛访问混进 Emby 页面。

多入口体验的实际目标是用户在局域网、外网、VPN 间换地址时保持同一服务和来源身份，同时让失效授权及时失效。未来可改善地址错误提示、候选连接耗时和手动入口，但不能通过“允许任意输入 URL 后直接转发全部凭据”来减少点击步骤。地址选择和身份核验应该被看作一个不可拆开的操作。

## 9. 生命周期与迟到回调：为什么不只检查 mounted

BIF、弹幕、资料助手和 OPED 都包含异步请求。mounted 只能说明某个 Widget 还活着，不能说明用户仍在同一账号、同一来源或同一次播放。用户在请求期间切账号、重新授权、切集、换媒体版本、导入字幕，甚至只是刷新直链，都会改变一部分上下文。安全处理的难点是既不能把旧结果挂到新视频，也不能因无关元数据对象变化把当前视频的增强能力永久清掉。

[FlyBifAccess.capture](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_bif_service.dart:38) 捕获飞翔 session 对象、source ref 和 scope epoch。每次确认有效时重新检查 session 仍相同、epoch 未变、当前 sourceRef 与原来源逐项一致，并叠加宿主传入的 isCurrent。Windows 宿主再检查 source-change generation、BIF generation，以及 [FlyBifPlaybackIdentity](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_bif_service.dart:18) 的四个稳定字段：statsScope、itemGuid、mediaGuid、loadNonce。

这个身份组合刻意不包含 source 对象自身。曾经使用 identical(source, currentSource) 时，导入外挂字幕、选择本地音轨、直链刷新返回 copyWith，就会让正在播放的租约被下一轮统计采样停止，同时清空 NAS 路径，且没有新的解析触发点。本次修正为稳定身份加两层 generation，并增加相应回归测试。真正切集或重进会改变 generation/loadNonce，仍会清掉旧资源；同文件的普通元数据复制则保留增强能力。

Android 的 [NativePlayerBridge](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/native_player_bridge.dart:219) 还需要核对反向 MethodChannel 的 bind token 与 context_id。一个旧原生 Activity 延迟回来的解析结果，不能交给已复用同一 Flutter engine 的新宿主。原生 NativePlayerActivity 再检查 activityDestroying、flyBifContext 与 canonical 私有路径。平台本地 BIF store 也有自己的 generation，在后台解析线程结束后拒绝已经过期的数据。

| 变化 | 是否应结束原 BIF 上下文 | 主要理由 |
| --- | --- | --- |
| 换飞翔账号或来源绑定 | 是 | 授权与缓存所有者变化 |
| 切单集、切实际媒体版本、重进播放 | 是 | 文件与播放上下文变化 |
| 原画改成未证明的派生流 | 不再复用原文件增强 | 时间坐标未证明兼容 |
| 同文件直链续签 | 否 | URL 可变而文件身份不变 |
| 同文件外挂字幕、本地音轨元数据复制 | 否 | 不应破坏缩略图和租约 |
| Activity 销毁或 bridge 被新宿主占用 | 是 | 旧回调已没有可写的宿主 |

未来如果给后台请求添加重试，应把以上所有者一起捕获，不能只在成功后检查页面标题。重试也不能无限期延长旧资源的可见寿命；有效性应在请求前、网络返回后、文件验证后和挂接 UI 前分别检查。当前 BIF 下载链已经采用这种逐阶段确认，缓存写入前后也有检查。

## 10. 本地统计数据库：事实、聚合与来源

[SqflitePlayStatsDatabase](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/play_stats/play_stats_database.dart:47) 当前 schema version 为 4。默认库名为 play_stats.db，统一账号绑定范围使用独立散列文件名。Windows 测试 profile 下的实际目录为 .runtime/bif-integration/support/databases。历史事实与同步元信息放在同一个作用域数据库，避免快照成功了但来源关系留在另一份不一致文件中。

库中既有 play_history，也有 video_stats、season_stats、anime_stats 等聚合表。play_history 记录某一次会话的稳定 history_id、远端媒体元数据、开始结束时间、实际观看毫秒、最大位置、观看与完成标志、OPED 状态和前后拖动次数。聚合表用于报告和汇总，不应在跨服务同步时取代原始事实。只上传一个“本月总计”无法可靠处理历史更新、去重、恢复和重新归属。

| 表或结构 | 角色 | 分析时关注点 |
| --- | --- | --- |
| play_history | 单会话事实 | history_id 不随重试改变 |
| video_stats、season_stats、anime_stats | 派生汇总 | 按旧事实与新事实差值更新 |
| fly_datasets | 事实来源数据集 | origin_kind、修订水位、已确认账号 |
| fly_record_provenance | 每条事实来源信封 | dataset_id、record_revision、source_ref |
| fly_write_context | 当前安装的新写入 epoch | 复制旧库后新事实不能伪装成旧来源 |
| fly_scope_binding | 数据库归属确认 | scope digest 不可被另一账号覆盖 |
| fly_sync_state | 稳定待上传包 | stream、seq、pending_json、最后成功时间 |

数据库打开时创建新的本机写入 epoch，把后续新事实指向新的 native dataset。旧导入事实保留原来源，不因为用户今天登录了某个账号就自动变成该账号的“新数据”。bindMediaBinding 只把当前安装的新写入 epoch 关联到已经核验的统一绑定；手工导入历史需要明确确认或与服务器已有数据集做精确匹配。这可以避免复制数据库造成两份客户端以相同来源身份继续制造不同事实。

[DefaultPlayStatsRepository.persistFinalizedSession](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/play_stats/play_stats_repository_impl.dart:31) 在事务内先读取同 history_id 的旧记录，再插入新事实并更新聚合。来源信封补入 binding、远端 item、series、season 等信息，已有信封不会被任意覆盖。聚合更新器按新旧差值计入 watchedDelta，重复 flush 不应把同一段观看时长重复相加。季与系列元数据后来纠正时，还需要重新计算受到影响的旧季和新季汇总。

## 11. 观看时长、观看次数、完成次数的当前含义

[DefaultPlayStatsSessionController](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/play_stats/play_stats_session_controller.dart:78) 使用连续媒体位置增量统计观看，而不是把“点击播放至退出”的墙钟时间当成观看时长。暂停样本更新基准但不累加；用户拖动后首个样本不累加；过大的位置跳变也不按观看累加。当前允许的连续进度差上限为 3000 ms。播放器缓冲、暂停和跳转都可能让墙钟时间与媒体实际推进不同，因此这不是可互换的指标。

记录同时保存 watchedMs、maxPositionMs 和 maxProgress。watchedMs 的精确口径是满足连续性条件的有效媒体推进量；倍速播放时按媒体 delta 累加，不等同于墙钟经过时间。用户拖到十二分钟后仅继续推进一分钟，最大位置可以很大，但新增观看事实仍只是一分钟。测试时用户在飞牛轻音第 3 集上的记录正是这个例子：最大位置为 760000 ms，本地 watchedMs 为 71000 ms。不能据此断言墙钟恰好看了七十一秒，也不能把最大位置直接当已观看时长。

当前 countedAsView 的阈值是：有有效时长时，单集观看累计达到时长的 20%，电影达到 10%。countedAsCompleted 在时长有效时要求最大进度达到 80%，并且满足“最后一次 seek 后至少三秒实际推进”或“播放器明确报告结束”之一；未知时长时依靠真实结束观察。这里的“完成”是当前产品统计规则，并非逐帧看完的严格证明。后续若希望“看完”意味着实际覆盖区间累计达到某比例，应新增覆盖模型与规则版本，不能悄悄改变历史字段含义。

~~~dart
// play_stats_session_controller.dart 中完成判定的实际摘录
final countedAsCompleted = mediaDurationMs <= 0
    ? session.playbackCompletedObserved
    : session.maxProgress >= 0.8 &&
          (session.playedAfterLastSeekMs >=
                  _completedAfterSeekThresholdMs ||
              session.playbackCompletedObserved);
~~~

[NativePlayStatsRecorder](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/play_stats/native_play_stats_recorder.dart:26) 补齐 Android 原生播放壳的本地统计。它区分“解析了下一集的元数据”和“下一集真的开始播放”：resolvePlayback/reloadServerSession 的结果只进入元数据缓存，不能因为预取就切统计会话；recordProgress 才是正在播放的可信信号。默认每五个样本 flush，一次会话在重复 flush 中维持同一个 history_id。暂停期间原生壳仍持续发进度心跳，因此不会因为用户暂停三十秒就把会话切碎。

原生记录器另有三十秒无事件的空闲看门狗，用于没有明确退出信号时收口本地会话。它与 NAS 任务的七十五秒活动租约不是一个机制：前者管理本地历史事实，后者保护后台工作不干扰用户。两套超时相同与否不构成错误，关键是各自拥有明确的事件源与语义。

## 12. OPED 计数与已发布跳过动作不是一套数据

本地 [LocalOpEdTracker](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/play_stats/play_stats_session_controller.dart:344) 统计“识别过区间”“明确跳过”“没有跳过”“区间播放时长”。它接收当前片头片尾范围，只对连续推进与范围的交集累计 opPlayedMs/edPlayedMs。用户 seek 的跨越不当成正常播放，暂停不累计。markSkip 设置明确的 skipped 标志；markDismiss 表示用户忽略提示，但并不等价于真的完整观看。

opNotSkipped/edNotSkipped 的当前判定不是“没有点跳过按钮就算没跳过”。如果区间不存在或已明确 skip，就返回 false；否则累计区间播放时长达到该区间长度的 80%，才计为 not skipped。此实现仍是媒体增量累计，重复回看某段可能继续贡献区间播放毫秒；如果产品希望表达“唯一时间覆盖比例”，需要另建覆盖区间集。分析者应避免把这套指标理解为精确逐帧覆盖证明。

已发布 OPED 的 /oped/actions 则是另一个在线事件协议。它记录 intent、settled、failed、cancelled，包含 action_id、source ref、文件修订、坐标、发布集修订、segment_id、generation、当前位置与目标位置。当前桌面 _finishFlyAction 负责上报终态，并没有自动把该网络事件转换成任意一组本地统计字段。不能未经核对就宣称每一个服务器 settled 事件都已经一对一改变旧本地 opSkipped 汇总。

这两套数据应该在文档、页面和后续统计设计中显式区分。本地计数强调离线可用和传统播放器兼容；发布动作强调服务器核验过的区间是否被实际执行。未来若需要统一报表，可以以稳定 action/history 关联或规则版本做归并，但应保留原始事实，防止一次自动跳过既被本地计数又被服务事件重复累计。当前版本没有把这项未来归并伪装成已完成能力。

## 13. 完整快照协议与离线恢复

[FlyDataSyncStore.preparePacket](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_data_sync_store.dart:212) 在数据库事务内生成完整快照，并把同一批次的 JSON 字节保存到 fly_sync_state.pending_json 后才发网络请求。只要该字段不为空，下一次重试返回原来的 JSON，而不是用更新后的历史重新生成相同 seq 的不同内容。这个设计保证服务端的幂等检查有稳定输入。

快照 schema_version 为 fly-snapshot/1，含 stream_id、snapshot_seq、创建时间、per_dataset_transaction 一致性声明、数据集 manifest 与 records。manifest 声明每个数据集的 schema version、export_revision_watermark、deletion_generation；记录携带 origin_dataset_id、origin_record_id、record_revision、legacy_payload 以及 source_ref、metadata_snapshot、quality_flags、rules_version 等来源信封。数据集和原记录 ID 不会因为更换服务入口地址而重建。

当前实现对单范围完整快照设有上限：数据集数量不超过 4096、历史不超过 10000 条、序列化包不超过 8 MiB。超过上限会停止创建本次快照并给出可操作错误，而不是截取前若干行然后谎称全量同步成功。这是当前 P1 设计的容量边界，适合分析后续分片或增量协议，但任何扩展都必须保留幂等、删除屏障和来源归属约束。

~~~mermaid
stateDiagram-v2
  [*] --> LocalFacts
  LocalFacts --> PendingPacket: 事务生成并落盘
  PendingPacket --> Sending: 发出相同 stream 与 seq
  Sending --> PendingPacket: 网络失败或未确认
  Sending --> Applied: status=applied 且 seq 匹配
  Applied --> LocalFacts: 清 pending、seq 加一
~~~

[acceptReceipt](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_data_sync_store.dart:306) 仅在服务器明确返回 applied、snapshot_seq 匹配且带有效 applied_at_ms 时清 pending 并推进序号。连接通了、HTTP 返回某个 JSON，或者服务器只说排队成功，都不能当成持久化完成。上传成功也不删除本地 play_history；后续完整快照仍包含这些事实，这是预览服务转正式服务时能够补传的基础。

[FlyDataService.syncNow](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_data_service.dart:475) 先排空本地写入、确认作用域，再选取或新建上传流，准备稳定包，注册缺少的数据集，检查已退役数据集与删除代数屏障，最后提交 /sync/batches 并接收回执。若已有待重试包属于另一个 deviceKey，不会悄悄改包或新建身份上传，而是保留并要求先正确处理旧设备的批次归属。

## 14. 多来源后台同步与预览转正式

[backgroundRefresh](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_account_controller.dart:418) 既处理当前绑定，也遍历该账号曾经使用过且仍在绑定列表中的来源。对于不是当前活动媒体连接的来源，使用 [syncStoredBinding](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_data_service.dart:359) 打开固定统计范围，并以 createWriteEpoch=false 避免一次上传动作意外制造新的事实来源。它只处理已有且已归属当前账号的事实，不因为上传历史而重新申请媒体播放权限。

后台刷新有节流与失败退避，不让每个小 UI 重建都触发全套同步。异常被转换为安全消息，播放能力不被拖住。切账号和传统模式变化会提升同步 epoch，旧循环即使刚完成网络调用也不能继续处理新账号的其它绑定。固定数据库 handle 与动态当前账号之间的关系是这段代码的重要审查点：不能把一个长 await 后的“当前数据库”当成开始同步时那一份。

本次测试为保护真实用户记录，使用只读 SQLite 连接核对独立 profile。Emby 紫罗兰测试记录保存了 50000 ms，飞牛轻音真实观看保存了 71000 ms，两份数据库当时均没有 pending_json，且都有预览服务的 applied 回执。本地记录、provenance 和数据集仍完整保留。公开 identity 读数确认 8796 与 8787 的 service instance 相同；Root 还只读确认正式设备表中没有这一新测试 installation，因此正式登录会创建新的 deviceKey，进而使用新上传流完整重传同一批事实。

“切服务地址”不能替代上述正式登录。预览服务中创建的 token、设备和 stream 可能根本不存在于正式数据库；直接换 URL 复用它们会遭认证或 stream 归属拒绝。正确路径是在保留本地 profile 和预览备份的前提下，通过真正登录正式服务，保持相同用户与 binding，再观察新设备、新 stream 与 applied 回执。Root 随后已通过真实 GUI 登录正式 8787 并进入飞牛首页，触发两来源自动完整补传；只读审计确认八条记录 applied、本地两个范围都没有 pending。具体三条关键记录、设备与证据见第 26 节。

## 15. 弹幕：原来源、NAS 优先、仅 NAS 与手动复用

当前弹幕并非只有“从 NAS 下载一个文件”这一条路。[DanmakuSourceStrategy](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/danmaku/models/danmaku_settings.dart:131) 有 original、nasPreferred、nasOnly，默认 NAS 优先。自动匹配、已保存在线源、用户明确导入的本地文件和 NAS 已确认数据具有不同语义，不能全部作为同等级的“缓存”抢先返回。

[NativeDanmakuPrefetch](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/native_danmaku_prefetch.dart:75) 的实际顺序是：非 original 模式下先尝试用户明确导入的本地文件；然后按精确 statsScope/item/media source 请求 NAS；NAS 成功就写统一 payload；nasOnly 在未取得 NAS 或本地导入结果时直接返回，不请求也不复用弹弹play来源；NAS 优先失败后才进入原来源逻辑。旧“激活的保存源”可能只是自动匹配保存的在线结果，所以不能无条件压过用户选择的 NAS 优先策略。

[FlyNasDanmakuCache.resolve](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_nas_danmaku_cache.dart:111) 只读取后端已经确认的匹配，不按标题重新匹配、不在客户端启动后台采集作业。它携带 binding_id、remote_item_id 和可选 remote_media_source_id 请求 /danmaku/resolve，ready 后核对 match_id、revision、version_key；payload_url 必须恰好等于由这些字段构造的同服务固定路径。客户端不会把 bearer 发给响应中随意给出的完整 URL。

自动起播的 NAS 读取总预算约 1200 ms；Windows 用户主动“重新获取 NAS 弹幕”使用独立的十二秒预算，失败保留原有弹幕，不把起播预算机械套在人工等待操作上。流式 JSON 上限 8 MiB，项目数量上限 100000，单条文字最多 1000 字符。每条时间、颜色和模式都必须合法；当前只接受滚动、底部、顶部对应的 1、4、5。任何一条畸形数据都不会半解析后把残缺结果当成完整版本。sourceKey 组合 match、revision、version，便于辨识到底显示哪个已确认版本；来源标签会清理控制字符并限制长度。

Windows 的 [_reloadNasDanmaku](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/desktop/playback/desktop_playback_screen.dart:788) 提供手动重新读取入口，状态区分未登录、未绑定、目录中没有条目、未关联、陈旧、禁用、超时、请求失败和格式失败。自动读取失败应安静回退；用户主动点击重取时，则需要说明应该去后台对应单集获取、复用或重新确认。已保存弹幕在后台由何种供应商获取、如何人工选择，是后端工作区职责；客户端消费链不应假装自己已经执行了后台的匹配确认。

### 15.1 后台已保存复用与客户端重新读取的衔接

“NAS 自动”“手动读取”“复用已保存弹幕”是三个相接但不同的动作。客户端的 NAS 优先策略自动读取当前精确来源的已确认版本；播放器里的手动按钮重新读取同一消费端点；后台工作区的已保存复用则由用户挑选已存在的弹幕资源并明确确认给当前来源使用。后一个动作会在服务端生成独立的目标匹配结果，随后客户端仍然通过原有 resolve/payload 接口取得数据，不需要在 Dart 增加跨来源猜测逻辑。

后端提供 GET /danmaku/saved 列出可用候选，POST /danmaku/reuse 执行明确复用。它们属于后台管理和媒体工作区交互，不在第 24 节的“当前客户端实际调用端点”中冒充已实现原生按钮。用户可以先在后台为目标单集确认，回到播放器点“重新获取 NAS 弹幕”，或者下次正常起播时由 NAS 优先策略消费。这个流程复用已保存正文，不必再次访问供应商或创建抓取任务。

已保存弹幕复用保留出处、原始获取时间和校时信息，目标与源拥有独立删除语义。它能帮助 Emby 与飞牛的同集内容共享已经确认可用的评论，但人工选中同名节目仍不等于两份视频字节相同。后端把这种人工复用标记为 manual_unverified_file，不能把它升级为 BIF、OPED 所需的原文件身份校验。弹幕可以通过人工偏移适配版本差异；自动跳过和整集 BIF 则依赖更严格的文件修订与时间坐标，这条区别必须保留。

当前播放器没有直接改写后端匹配数据库的捷径。遇到 NAS 未关联、陈旧或禁用时，自动播放按策略回退，手动入口显示可操作状态；用户去后台确认后再读取得到的新版本，仍会经过 source、revision、version_key 与晚回调检查。读取失败时保留已经显示的弹幕，成功并确认上下文仍有效之后才替换。这样既避免等待一次网络请求时画面突然清空，也避免在切到下一集后把上一集的结果安装进去。

## 16. BIF manifest：完整文件身份与覆盖

[BIF 解析入口](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_bif_service.dart:95) 只接受 status=ready、verified FileContext、精确匹配 source_ref、合法 asset 的整集结果。missing、stale、disabled 或失败都保留原预览行为，不阻塞视频。此处没有“只要拿到若干帧就显示为整集完成”的捷径；六十秒试样和未发布检查点不能被客户端误认为完整资产。

POST /api/v1/bif/resolve 的请求体包含 source_ref。ready 响应的 file_context 与 OPED 共用文件契约，至少用于检查 identity_state、source_ref、file_revision_id、media_coordinate_id 和 duration_ms。asset 则含 id、同服务相对 URL、sha256、bytes、frame_count、coverage_start_ms、coverage_end_ms、duration_ms、width、height、interval_ms。客户端将这些字段看作需要核验的合同，而不是可自由拼接的展示信息。

| 字段组 | 当前检查 |
| --- | --- |
| 状态与来源 | ready；FileContext verified；source ref 三字段相等 |
| 文件坐标 | file revision 与 coordinate 非空，duration 为安全正整数 |
| 整集覆盖 | start=0；end=FileContext duration；asset duration 同值 |
| 资源身份 | UUID 格式 id；裸 64 位十六进制 SHA |
| 容量 | 80 bytes 至 128 MiB；1 至 200000 帧 |
| 图片与采样 | 宽高为正且不超过 4096；interval 为正整数 |
| 下载 URL | 相对同服务固定 assets/{id}/content 路径 |
| 查询参数 | source 字段逐项唯一、相等；拒绝额外或重复字段 |

飞牛目录时长 1421000 ms 与真实文件 1421005 ms 的差异不会被客户端直接比较。解析器比较的是同一 resolve 响应里的 FileContext duration 与 asset duration、coverage end；如果后端 FileContext 使用证明绑定的真实时长，两者一致就通过。若响应内部一个字段用目录取整值、另一个用文件真实值，拒绝是合理的合同保护，应该修正服务端契约来源，不应通过放宽“整集覆盖”去掩盖不一致。

asset.id、文件 SHA 和 source ref 承担不同工作。UUID 负责定位发布资产，SHA 负责核验字节，source ref 负责当前用户从当前绑定读取的授权关系。即使两个来源复用同一 BIF 字节，也仍应在下载查询中核对各自的精确来源；不能把“已经有这一 SHA 的缓存”扩展成允许任意账号读取任何来源。相应的服务端授权仍是必要前提，客户端只增加第二层防护。

## 17. BIF 受控下载、校验与私有缓存

[FlyDataApi.bifBytes](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_data_api.dart:144) 是专用二进制下载入口。它再次校验相对路径只能落在 /api/v1/bif/assets/{uuid}/content，不能有 scheme、authority 或 fragment，声明大小必须在允许范围。请求使用独立严格 TLS 的 Fly API transport，禁止重定向，只接受 200，并把响应当成流读取。Content-Length 存在时必须等于 manifest 声明；即便没有长度头，也按每个 chunk 累积大小，超过声明立即失败，最终长度必须完全相等。

这个设计解决的是一整条数据路径的凭据和资源边界。把 Fly bearer 放到现有 Image.network、Glide 或媒体图片下载器里，再让服务器响应任意 URL，会让媒体域的证书例外、重定向、缓存键和账号归属混在一起。当前方案只在受控服务根地址下下载完整资产，平台 UI 得到本地路径，不得到新的 Fly header；原媒体 headers 仍只供原媒体预览回退使用。

[FlyBifAsset.accepts](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_bif_service.dart:176) 不只检查 SHA。它还检查 BIF magic、version、frame_count、索引结束位置、零时间首项、终止 sentinel、每个偏移的严格递增和边界、时间戳严格递增、最后偏移等于文件总长，并要求每帧时间小于真实文件时长。损坏索引不能因为 JSON manifest 看起来正确就交给原生壳任意切片。

[FlyBifService.resolve](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_bif_service.dart:235) 的缓存键散列 service instance、user、精确 source、文件修订、坐标、asset ID 和 SHA。Windows 本次私有目录为 .runtime/bif-integration/cache/fly_bif；Android 为应用 cacheDir/fly_bif。缓存命中也重新校验长度、SHA 和完整索引，磁盘文件不是永远可信的。验证由 Isolate.run 执行，避免整份数据的散列工作直接堵在 Flutter 主 isolate 上。

下载后先写带时间后缀的临时文件，再次确认当前上下文有效，随后原子式重命名为正式缓存文件。Windows 若已有损坏目标文件，先移除该特定缓存条目，再重命名；不是清空整个用户目录。失败或过期结果在 finally 中尽力清理临时文件。缓存最多保留十六份资产，按修改时间删除较旧的其他条目，不按用户历史数据库大小作决策。这里的清理对象只有可再下载 BIF，不包括账号、统计或用户手工文件。

需要承认的容量细节是：下载仍会把完整 BIF 聚合成内存字节，之后验证、平台解析和少量图片缓存也要占内存。128 MiB 是拒绝上限，不是“任何 128 MiB 文件都适合低内存设备”的性能承诺。当前真片成品仅约 1.14 MB，风险较低；未来若支持极长影片或高密度采样，应基于真实内存曲线决定是否改为文件流散列与索引映射，而不是只提高上限。

## 19. Android BIF 时序与原生边界

Android 不直接复用 Windows 的 Widget，但共享 Dart 的授权、manifest 验证、严格下载和 SHA 校验。[NativePlayerBridge 的 resolveFlyBif](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/native_player_bridge.dart:219) 接收 context_id、statsScope、itemGuid、mediaGuid、originalFile、paused，先核对原生宿主当前绑定 token 和 scope，再捕获 FlyBifAccess、启动该上下文的活动租约。只有 originalFile 为 true 时才解析 BIF，返回也只能是仍然当前的本地路径。

[NativePlayerActivity.resolveFlyBifContext](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/android/app/src/main/kotlin/com/geqian/flyplayer/fly_player/NativePlayerActivity.kt:10134) 先停止旧上下文，为新播放生成 UUID context，并通过 NativePlayerReverseBridge 请求 Dart。回调回到 UI 线程时，必须保证 Activity 不在销毁、context 仍匹配、结果是非空字符串；随后对 File 做 canonicalFile 解析，只允许位于应用 cacheDir/fly_bif 之下的真实文件。这比字符串包含某个目录名更严格，避免路径穿越或另一个缓存域的文件混入。

~~~kotlin
// NativePlayerActivity.kt 中本地路径边界的实际摘录
val file = File(result).canonicalFile
val root = File(cacheDir, "fly_bif").canonicalPath + File.separator
if (file.path.startsWith(root) && file.isFile)
    seekThumbNasBifStore.prepare("", emptyMap(), file)
~~~

原生壳保留独立的 NAS store 与原 Emby store，渲染时优先使用准备好的 NAS 数据。转换源时清除已解码帧的来源标识和 bitmap LRU，避免两个 store 中相同帧下标被当成同一图片。原有 Emby URL、headers、章节 Glide 预取链仍保留，不把 Fly bearer 注入 loadArgs 或媒体图片头。跨原生边界的是一条已验证本地文件路径，不是让 Kotlin 获得任意飞翔 API 下载权限。

[SeekThumbnailBifStore.prepare](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/android/app/src/main/kotlin/com/geqian/flyplayer/fly_player/SeekThumbnailBif.kt:119) 新增可选 localFile。它沿用原后台线程和 generation 门控，在本地文件存在且大小合法时读取并解析；线程结束时仅把仍当前 generation 的结果发布。同 URL、同本地路径重用与切集清空的行为也在 store 层处理，不能仅依赖 Activity 因为“应该会重建”来避免竞态。

本次 Android 验证编译了完整 Kotlin 源并执行 BIF 相关 JUnit，没有安装新的 APK，也没有授权 ADB 设备可供手势、横竖屏、分屏、后台恢复等验证。所以可确认的是代码可编译、解析和竞态单测通过；不能写成“Android 已在飞牛视频上真实拖动看到缩略图”。若 GPT6pro 评估下一轮优先级，Android 实机应是明确待补的验证层，而不是默认已经被 Windows 结果覆盖。

## 20. 活动租约、暂停保活与后台让路

[FlyPlaybackActivity](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_playback_activity.dart:8) 为每次授权播放上下文生成随机 UUID session_id，调用 POST /api/v1/playback/activity。body 包含 session_id、playing/paused/stopped 状态及可选 source_ref。它不是历史统计事件，也不携带 watched_ms，更不拿后台 job ID 充当播放器 session ID。服务按认证用户、设备和 session 管理租约，保留七十五秒；客户端每十五秒续租，暂停仍续租，明确退出发送 stopped。

start 会立即发送当前状态并安装定时器；update 只在 paused 状态改变时触发即时续租，正常持续播放由定时器保活。每次心跳执行前检查捕获的访问是否仍当前，失效则走 stop。_queued 防止积压重复心跳，_pending 尾链保证网络事件串行。stop 先标记 closed、取消定时器，然后排在已发更新之后发送 stopped，因此客户端不会在本地终止后又被排队的 playing 心跳复活。

~~~dart
// fly_playback_activity.dart 中终止顺序的实际摘录
Future<void> stop() {
  if (_closed) return _pending;
  _closed = true;
  _timer?.cancel();
  _timer = null;
  return _pending = _pending.then((_) async {
    try {
      await _send(_event('stopped'));
    } catch (_) {
      /* lease expires server-side */
    }
  });
}
~~~

租约使用捕获的旧账号发送终止，而不是切账号后拿新账号清理旧播放。网络失败静默，不弹出阻断视频的对话框；客户端请求有三秒限时并关闭独立 API。进程崩溃、网络突然断开或系统杀进程时可能来不及发 stopped，所以服务端过期仍是最终清理保障。文档不能把“正常退出发 stop”描述成任何故障下都会瞬时释放。

后台夜间计划、CPU/内存限制、检查点、任务重入以及当前是否允许解码，是服务端 worker 的职责。客户端仅报告真实活动，不能因为用户暂停就假装离线让 worker 抢资源。本次服务试验约 1.35 秒内观察到播放引起 FLY_PLAYBACK_ACTIVE，让路后保留已完成分段；暂停超过三十秒仍受保护，再次尝试运行被快速拒绝。用户后来真实接管测试窗口播放轻音，另一个新活动租约再次让任务让路，这属于正确保护真实使用，而不是客户端幽灵心跳。

0.75 CPU 核、512 MiB、无 GPU 是本次 NAS worker 硬限制，不是给 Windows 视频解码器施加的同一限制。客户端可以使用已有硬件视频解码；实际采样显示未满载，但该短采样不能证明所有画质、机器与整集时间里的最大负载。产品文案和后续自动调度应分别说清“后台资源上限”“播放检测”“客户端播放负载”。

## 21. OPED 已发布版本的执行与 ED 尾部保护

当前 OPED 基础来自 0ff973b，而不是 B 树后续 dirty 设置。[FlyOpedSet.parse](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_oped.dart:95) 要求 status=published、请求的 playback_context_id 和 generation 回显一致、FileContext verified 且 source 匹配；文件修订、坐标、发布集修订和正时长都必须存在。每个 segment 要有唯一 ID、合法边界、允许的 kind 和 skip_policy；区间不得互相重叠，可跳过区间不得撞入 protected_ranges。整套发布数据原子接受，不能只挑合法部分执行。

当前支持的 kind 包括 op、ed、recap、preview、post_credit，但自动/提示入口的 at 查询只选 op 与 ed，且 policy 不为 never。auto、prompt_only、never 表达不同执行意图，受保护尾部不能因为靠近片尾就被旧倒计时吞掉。派生流、下载文件和外部本地文件不借用未经证明兼容的原文件区间。

[FlyOpedPlaybackPolicy](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/services/fly_data/fly_oped.dart:189) 只在连续向前推进、首次跨入区间、位移不超过 2500 ms 且 policy=auto 时允许自动触发。续播直接落入区间、用户 seek 后、反向跳转、较大跳变以及重复进入，不会直接重演自动动作。手动跳转会清除连续观察基准。这个限制旨在避免用户已经主动选择的位置被自动规则反复夺走。

Windows [_skipPublished](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/desktop/playback/desktop_playback_screen.dart:1989) 在真正 seek 前重新 resolve 当前发布，并要求仍为同一出版内容；若区间被撤销或修订，就取消提示并说明不可用。执行动作先产生 intent，再把目标交给播放器，随后观察实际 mpv seeking 状态和 time-pos。命令 Future 完成不等同于已经落到目标；只有真实位置在目标附近五百毫秒且引擎停止 seeking，才形成 settled。动作最多一个终态，超时或上下文改变产生 failed/cancelled。

ED 动作还会设置尾部保护并取消旧自动下一集倒计时。flyOpedAllowsAutoNext 的条件保留真实结尾或明确允许的状态，暂停不能靠近尾部就跳下一集。Android 的 [FlyOpedPlayback.kt](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/android/app/src/main/kotlin/com/geqian/flyplayer/fly_player/oped/FlyOpedPlayback.kt:16) 有对应的发布校验、进入策略与 seek epoch 观察。B 树新增的账号级 OPED 设置、时间线显示和原生设置传递仍须另行评审，本文没有把这些未提交文件当作当前可用界面。

## 22. 人物遮罩：已经存在的本地能力与本次边界

BIF 缩略图和弹幕人物遮罩处理的是不同问题。BIF 是按时间查找视频小图，用于进度条预览；人物遮罩决定弹幕哪些像素不覆盖人物。下载一个 BIF 不会自动给出分割 mask，更不会把服务器生成缩略图的 ffmpeg 流程变成 AI 分割服务。本次业务改动保持遮罩代码不变，用户要求的 worker 无 GPU 也不能被解释成所有现有客户端遮罩实现都已经改成后台 NAS 推理。

Windows 当前 [DesktopDanmakuSegmenter](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/desktop/playback/desktop_danmaku_segmenter.dart:28) 从 media_kit 取得不含 libass 字幕的原视频帧，经 MethodChannel 调本地 MNN 分割；模型输入固定为 512×512，outputWidth 只控制返回蒙版尺寸。它核对 BGRA 字节与几何关系，返回 RGBA mask、显示尺寸及推理耗时。这个组件是现有本地实现，不能在文档中写成调用了 NAS mask API。

[DesktopDanmakuOverlay 的 mask timer](E:/fly_play_recovere/.worktrees/fly-player-bif-integration/lib/desktop/playback/desktop_danmaku_overlay.dart:224) 只在 Windows、弹幕启用、避让设置开启、确有评论时安排采样；暂停/缓冲时不启动新的推理，in-flight 标志阻止并发积压，generation 防止 seek 或设置切换后使用旧 mask。采样间隔被约束在 200–500 ms，旧图像被替换时及时 dispose。坐标映射还需要把视频 frame、mask 像素和实际显示区域对应起来，不能用未考虑裁剪/比例的简单拉伸覆盖。

Android 当前有 NativeDanmakuOverlayView、DanmakuMaskPrecomputePipeline、DanmakuPersonTrackerRuntime、时间戳和预算策略等本地链路。这里可确认有预计算/跟踪与 generation 保护代码，不表示本次已在设备上重新验证所有 Plan A/Plan B 行为。仓库的 nas-ai-mask-requirements-for-gpt6pro.md 属于需求与讨论材料；原主树、A 预取树和 B OPED 树还可能有独立实验。应把“当前实际分支实现”“其它树已有修改”“未来 NAS 方案”分别标记。

后续若让 NAS 提供人物遮罩，需要重新设计文件版本、时间坐标、mask 编码、质量门槛、采样与插值、断点、客户端退化、隐私和资源预算。可以借用 BIF 的身份/授权/晚回调框架，但不能直接复用 BIF 的 JPEG 资产格式或把黑色区域视为人物 alpha。GPT6pro 分析时应从已有本地性能瓶颈和实际设备效果出发，不建议仅因后台现有 ffmpeg worker 就把所有遮罩任务硬塞进同一作业。

## 23. 资料助手、LLM 与记忆的客户端范围

这一服务端行为可由 [RunCreate.use_personalization](E:/fly_play_recovere/nas-branches/bif-integration/backend/fly_data/assistant_api.py:46)、[require_personalization_reader](E:/fly_play_recovere/nas-branches/bif-integration/backend/fly_data/assistant_api.py:65) 和 [media_context](E:/fly_play_recovere/nas-branches/bif-integration/backend/fly_data/assistant_api.py:71) 核对；这里引用的是服务端集成树，与客户端 4b0e747 分别标记，不能把后端文件算作 Flutter 代码。

若后续接入个人化，必须同时明确用户选择、客户端能力声明、上下文读取、任务创建、轮询、取消以及退出时的所有者核对，不能只在创建请求里加一个布尔值就算完成。界面还需要让用户分辨公共资料与个人记忆，提供适当的来源和撤销路径。服务器关于记忆检索、隔离、版本、保存、归并和删除的实现，应阅读配套后端材料；当前客户端不执行这些管理操作。

面板关闭时递增 generation 并取消轮询；账号或播放来源变化后，旧请求不能继续向新语境写回。当前文件未验证时仍允许查询资料和保存服务端候选，但不能越过 OPED 的已发布门槛。后续可以改善等待原因、可撤销记忆提示、引用展示和多轮历史入口；这些属于产品扩展，应在服务器授权及记忆语义明确之后设计，不应通过客户端直接修改后端数据库实现“方便”。

## 26. 统计保留、预览到正式服务与真实使用记录

本次独立 profile 不应在实验结束后直接删除。用户曾在该窗口真实播放飞牛《轻音少女》第一季第三集，这不是可随意丢弃的测试填充数据。只读 SQLite 审计发现一条飞牛记录累计观看 71,000 ms，最大位置 760,000 ms；另一条 Emby 实验记录累计观看 50,000 ms。时间线最大位置和真实观看时长不同，说明 seek 到十二分钟没有把前十二分钟凭空计入观看。

两份来源数据库保留了本地历史、来源身份和记录 provenance，预览端已有成功回执，pending JSON 为空。这说明预览的上传已完成，也说明本地事实仍在；回执不会删除本地历史。本次正式与预览来自同一服务身份的快照，所以 accountKey 及原有绑定范围可以保持一致，但预览中新创建的认证设备和上传流不自动存在于正式数据库。Root 在正式端只读核验时，本安装 ID 尚没有登记设备，这进一步说明不能拿预览 token 或 stream 直接假设正式端认识它们。

正确的正式登录路径是通过真实客户端账号界面重新登录正式地址，使服务创建该安装的正式设备凭据和新上传流，再用已有完整本地快照补传。正式登录后还应按源逐一确认：新设备与 stream 属于正式服务，dataset 继承原本身份，记录 ID 没有被重新生成，已存在记录按幂等逻辑更新，成功回执推进本地状态，飞牛那条七十一秒事实可在正式端读回。不能只修改服务 URL 然后看到目录出现就宣布统计迁移成功。

这条路径也解释了离线设计的重要性。用户是否能回到原来的观看记录，不应该完全取决于某个临时后端活了多久。客户端保存的是可以重复上传的有归属事实，服务端回执确认某个完整状态已经接收，而不是把客户端当成一次性消息队列。反过来，任何旧设备尚未收妥的 pending packet 都需要先解决归属，不能在新设备上盲目继承旧包序号。这里既需要保留事实，也要保留“哪一个设备已经确认了哪一批事实”的协议边界。

## 28. 分支整理与 GitHub 发布建议

客户端和服务端是不同仓库，发布时分别给出远端地址、分支、提交、文档和产物，不把两个仓库放进一个提交。Root 统筹用户授权的推送；客户端按追加的明确授权将文档与业务分支推送至 [codex/bif-client-integration-20260914](https://github.com/huya688zdx/fly_player/tree/codex/bif-client-integration-20260914)，不改主分支。当前业务点是 4b0e747，验收和长文放入独立 docs 提交；实际远端提交需以 push 后 ls-remote 对比为准，并在交付回复中记录。这样审阅者能区分程序行为和验证说明，也能用业务提交复原现有 Release 构建。

整理原主工作区时，第一步应是保留未提交状态与来源记录，随后按功能建立能够评审的候选分支。人物遮罩、预取、OPED 设置、国际化文字等改动可能交叉修改 NativePlayerActivity、DesktopPlaybackScreen 和时间线组件，不能以“哪个目录更新日期较晚”为依据整目录覆盖。建议先把每项改动的目的、原始基准、已运行测试和未完成事项写清，再比较它与本次已提交代码的实际差异。

当前账号链已合入，因此无需再次从旧分支覆盖登录页面。旧 NAS 弹幕只取了消费补丁，也不应为了得到同一功能再次 merge 带有污染历史的祖先。国际化基础与兼容目录标签已继承，但新账号组件仍有未完全迁移文字；后续应以当前控件为基础补 key，而不是把旧页面整体替回。B 树后续 OPED 设置应重点核对 published 区间执行、ED 保护和稳定播放身份是否仍成立，不能因设置控件看起来独立而省略这些交叉检查。

## 29. 提供给 GPT6pro 的分析问题与交付判断

建议 GPT6pro 先按“已有证据能支持什么”阅读，再提出架构重构方案。当前整体方向是统一账号提供授权和增强能力，原媒体后端继续供给播放，文件级证明控制能够自动影响播放的内容。这个方向保留了原播放链的可用性，也留下多个 epoch 和来源身份需要严格配合的成本。分析时可以评估是否需要一个更集中、可测试的播放访问上下文对象，但不宜为了简化类数量而削弱账号、绑定、文件和单轮播放的不同生命周期。

第一组问题是账号与来源体验。不同入口最终是否回到同一当前来源？用户能否理解飞翔账号与原媒体账号的差别？更换服务器地址时，界面是否明确保留同一服务实例的身份检查？绑定失效、服务器不可达、设备授权过期时，是否能说明下一步操作而不暴露内部异常？这些问题应结合实际账号面板和现有 controller 处理，不应只从登录 API 表推导界面已经完备。

第二组问题是统计语义与迁移。观看时间、最大进度、观看次数、完成次数、片头片尾命中、明确跳过及服务端动作分别表达什么？重新安装、克隆服务、恢复备份、绑定重建和多个设备同时上传时，数据集及记录身份能否保持稳定？完整快照模式的上限、保留策略和错误恢复是否满足长期使用？任何优化都应保留本地事实可恢复和服务端幂等接收的前提，避免用“最后一次播放状态”替代历史事实。

第三组问题是预览与自动跳过的风险分级。BIF 失败可以无声退回原图，不应影响起播；OPED 一旦执行会改变用户观看位置，必须验证当前发布并确认实际落点；LLM 候选只能提示，不能因为置信度看起来高就自动变成已发布区间。三者可共享 FileContext 与访问捕获工具，但错误反馈、审核门槛和回退策略不应被统一成一种泛化“增强数据加载”。建议逐条检验这些语义边界是否还可以通过类型系统减少误用。

第四组问题是 UI 与可解释性。用户在飞牛视频上看到缩略图已经成立，但现在缺少一个普通用户可理解的诊断入口来区分 NAS 预览、原服务预览、章节图以及暂无预览。是否需要只在高级诊断中显示资产状态和更新时间，而不把 SHA、绑定 ID、文件坐标放进日常播放界面？同理，后台等待播放空闲可以用简单状态说明，详细检查点与 CPU 限额留在管理页。产品信息应服务用户决策，不应为了展示实现完整度而填满播放器。

第五组问题是跨平台和长期资源。Windows 的真实验证已经覆盖本次目标，Android 仍需要独立设备登录、起播、手势预览、后台切换、PIP、源切换和缓存清理验证。本地遮罩的性能验证与 NAS BIF 下载应分别组织，避免把后台低负载当成客户端分割低负载。若后续计划统一预览组件，应先明确 Dart 与 Kotlin 在位图释放、缓存和线程取消上的不同约束，再考虑共享解析模型。

本文支持的当前交付判断是：客户端业务已实现并通过自动检查，独立 Windows 真实飞牛播放出现了与 NAS 成品一致的首、中、末段进度条预览，真实播放与暂停会保护后台任务，退出会结束正常租约；正式服务登录后八条本地事实已取得 applied 回执，三条关键观看事实逐项一致。本次没有声明 Android 实机通过、整集连续观看完成、最后黑帧浮层截图已单独成立，或原主树及其它工作树的全部 dirty 成果已经合入。这些边界使后续分析和发布有可靠起点，而不会把待验证事项藏在笼统的“全部完成”里。

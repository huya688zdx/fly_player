# Fly Player：NAS 预生成弹幕人物遮罩需求

日期：2026-09-12。用途：直接交给 GPT-6 Pro 做可行性评估与最小实施规划。本文不是已经确定的技术方案，也不代表服务端功能已经实现。

## 给规划模型的任务

我正在开发 Fly Player，已有 Android 和 Windows 内置播放器，也在做一个部署于自家 NAS、管理播放数据的配套后端。我希望新增“提前生成人物遮罩”的能力：NAS 在空闲时分析视频，保存与视频时间轴对应的遮罩，PC 和安卓播放时直接读取，让弹幕经过人物时被遮住，改善人物漏遮、误遮、轮廓滞后和跳转后的残留，同时减少客户端实时推理负担。这里的遮罩只影响弹幕，不修改原视频，也不是把人物抠出后重新编码视频。

请结合下述现状，判断这条路线在低性能 NAS 上是否值得做，并给出可落地的最小方案。先评估与规划，不直接写实现代码。请明确区分事实、假设、建议和必须实测才能下结论的部分，不承诺“完美遮罩”或未经验证的生成速度。

## 已知环境与证据

- NAS CPU 是用户确认的 **Intel Pentium G4600**：2 核 4 线程、3.6 GHz，带 HD Graphics 630，支持 Quick Sync。系统为飞牛 Linux，已有 Emby 和实际媒体文件。内存、当前负载、容器权限及可用驱动尚未核实。硬件支持视频编解码加速，不代表当前 AI 模型能直接用核显加速。
- 当前 Android 网络播放走实时画面抓取再推理；本地文件有提前解码和遮罩预计算路径。新平板一次采集的网络抓帧加推理中位数为 **243 ms**、P95 为 **304 ms**，其中抓帧中位数仅 **7 ms**。本地带弹幕采集的非复用预计算步骤中位数为 **210 ms**，预计算领先播放位置约 **2.77 秒**。这些是平板数据，不能用来推算 G4600 的速度或功耗；243 ms 也不等于完整显示链路延迟。
- 当前模型是约 88 MB 的 `isnet-anime-512-fp16.mnn`，固定 512 输入。缩小最终保存的遮罩尺寸不等于降低这份固定输入模型的推理成本。主要素材是动漫；真人素材效果需要单独评估。
- 同一个模型的 Android 近似预后处理与上游流程已做同帧对照，结果有改善也有退化，尚未证明存在“整体更准且成本相同”的替代模型。提前计算可以改善时序，但不能自动消除模型漏检、误分背景等问题。
- 从真实 Emby 媒体库取得的两集 BIF 均为 **320×180、每 10 秒一帧**。BIF 本身是视频预览缩略图，不含人物遮罩。这个密度不足以持续跟随人物，不能仅靠保持旧轮廓或插值解决运动和切镜；可用于模型选样。若要连续遮罩，需要评估直接从原视频顺序解码、以更密频率取帧。
- Android 已有按视频时间戳选择遮罩、缓冲与 seek 清理的基础；Windows 已接入 MNN 人物遮罩绘制和 seek 失效，但目前使用最近返回的遮罩，还没有服务端遮罩时间索引。两端有可复用部分，尚不支持直接读取同一套 NAS 遮罩包。Windows 的真实连续播放画面对齐验收仍未完成。

## 希望达到的行为

1. 同一个具体视频版本只需生成一次，Android 和 Windows 内置播放器共用结果。客户端可以按播放位置预取、缓存和读取，暂停、倍速、前后跳转、回到零点与切集时正确对齐。
2. 视频照常由现有媒体服务器或本地文件播放，NAS 配套后端负责遮罩生成、状态及数据分发。原视频保持不变，不要求更换播放内核。
3. 遮罩服务故障、未生成完成、数据缺失或过期时，视频与弹幕应继续可用，不能卡住起播。需要规划何时回退现有端侧 AI、何时暂时显示普通弹幕，并处理切换时的旧遮罩。明确无人、缺帧、读取失败和切镜不能混为一种状态。
4. G4600 上可以接受离线慢速处理，优先保证日常 NAS、播放与转码体验。首版尽量单任务、可限制资源，并能暂停或中止；恢复时避免已有成果无意义重算。具体线程数、调度时段和限制方式由实测决定。
5. 遮罩必须绑定实际媒体文件版本及对应时间轴，不能仅凭片名、TMDB ID 或集数复用。处理不同剪辑、片头差异、转码时间戳变化、显示比例、裁剪、黑边与旋转，避免时间或空间错位。

## 请重点做出的规划决策

- **计算放在哪里**：比较 G4600 独立离线生成与“性能更好的 PC 生成后上传、NAS 保存分发”。先给一个推荐的最小主方案；PC 代算可以是后续选项，不要起步建设分布式计算框架。NAS 上有媒体不等于后端容器已能访问，应说明最小访问条件。
- **模型与运行库**：现有模型能否作为基线？是否有适合动漫、质量更好且 G4600 能接受的候选？说明权重、授权、输入契约、CPU 指令集和运行库兼容性；核显加速单独验证。不要只按参数量、文件大小或其他硬件跑分排名。
- **时间与画面质量**：建议如何选择采样密度、输出分辨率、边缘处理及切镜策略？每秒 5 张与 10 张只是候选对照点，不是已确定要求。说明低密度在快速动作中的限制；运动补偿或自适应采样只有收益可证明时再引入。
- **保存与分发**：比较适合随机跳转的分段压缩灰度帧、遮罩视频轨道等少量可行方式，选出最小实现。给出必要的媒体身份、时间索引、尺寸和版本信息，以及跨端缓存和读取流程；控制存储、带宽与客户端解码成本。不要先铺设庞大通用协议。
- **接入边界**：指出 Android 与 Windows 现有链路能复用什么、必须改什么。Android 当前零点 PTS 判定、填满裁剪和旋转需要核对；Windows 要补按播放时间选帧。灰度遮罩需正确转成渲染透明度，不能把灰度图片直接显示就视为完成。
- **落地预算**：提出在这台 NAS 上实际测量的方法，并据测量估算每集生成时间、峰值内存、资源占用、存储和客户端成本。需要哪些尚缺信息，请集中列出，避免用假定硬件能力代替测量。

用于核对预算的算术示例：24 分钟、每秒 5 次推理共 7,200 次；假设单次推理为 0.2／0.5／1 秒，纯推理分别需要 24／60／120 分钟，尚不含解码、预后处理和压缩。若每张保存为 320×180、8 位单通道，未压缩共 414,720,000 字节，约 395.5 MiB。以上均不是 G4600 实测，压缩后大小必须另测。

## 范围与验收要求

首轮重点是 Android 与 Windows 内置播放器、NAS 中可访问的动漫文件。macOS、Linux 客户端、外部 PotPlayer、直播、公网多租户和全媒体库自动调度不作为首版必做项。沿用此前家庭 NAS 后端的规划边界，既有播放统计的本地采集及低频同步不在这次改造范围；这只是既有约定，不代表本轮核实过后端部署状态。已有弹幕搜索、匹配和外部入口冷启动问题另行处理，不借本需求重写弹幕系统。

请先规划一个 **1–2 分钟代表性片段的小样验证**，覆盖静态人物、快速运动、切镜和无人场景，并据此给出继续或调整路线的判断标准。验收需要两端实际叠加弹幕观看、跳转与倍速操作，以及可对照的生成时间、资源占用、体积和读取成本。分开评估模型质量与时间对齐；不能用“遮罩面积更大”“弹幕 FPS 正常”或“构建通过”代替视觉验收。

期望输出是一份短而具体的规划：可行性判断与主要瓶颈、推荐方案及必要取舍、最小数据契约和跨端接入点、小样验证步骤与验收标准、阶段划分、缺失信息及风险。除确有必要外，不新增框架、兼容层、配置体系或大套测试基础设施。
